# Calling a DLL

Here is my approach. I am not sure whether it is entirely correct, but it works, haha. I followed the official third-party library example.
![](/media-occurrence/blog%3Acnblogs-19174295%3Amedia%3A1)
I will skip the DLL packaging process and focus on what to do once you have the DLL and Lib.
For example, use TestThird, a plugin created from the official template.
Place the dll and lib files in `TestThird\Source\ThirdParty\TestThirdLibrary\x64\Release
Then place a dll in `TestThird\Binaries\ThirdParty\TestThirdLibrary\Win64`.
This step could theoretically be improved, for example through automatic copying, but I have not investigated it yet.
After adding the files, add the following to the module's Build.cs:
![](/media-occurrence/blog%3Acnblogs-19174295%3Amedia%3A2)
Finally, add an .h file with the same name as the dll to the module to declare the functions you can call in the dll.
![](/media-occurrence/blog%3Acnblogs-19174295%3Amedia%3A3)
If you do not know which functions the DLL contains, download [Dependencies](https://github.com/lucasg/Dependencies).
![](/media-occurrence/blog%3Acnblogs-19174295%3Amedia%3A4)

Drag the DLL into it to inspect the functions. Very convenient.
Finally, call FPlatformProcess::GetDllHandle when the module loads. I modified my version slightly; it is roughly like this.
Do not copy this directly: I changed it temporarily for illustration. In practice, it should receive windll, macdll, and linuxdll.
![](/media-occurrence/blog%3Acnblogs-19174295%3Amedia%3A5)
Remember to call FPlatformProcess::FreeDllHandle when the module unloads.
![](/media-occurrence/blog%3Acnblogs-19174295%3Amedia%3A6)
You can now include the header and call the functions normally.
![](/media-occurrence/blog%3Acnblogs-19174295%3Amedia%3A7)

## Addition: Windows header conflicts
A Windows third-party library in UE5 may include Windows SDK headers indirectly and leak macros or platform types into later UE headers. Start with the first error and include chain rather than treating every `_Interlocked*` error as a separate cause.

Isolate third-party includes in Windows-specific implementation files using your engine's platform wrappers. The original notes use this layout; it was not compiled in this editing pass:

```cpp
#if PLATFORM_WINDOWS
#include "Windows/AllowWindowsPlatformTypes.h"
#include <winsock2.h>
#include <ws2tcpip.h>
// Include third-party headers that need Windows types here.
#include "Windows/HideWindowsPlatformTypes.h"
#endif
```

Winsock2 should generally precede windows.h that might introduce old winsock.h. Check whether your UE version requires WindowsHWrapper or additional macro wrappers. Do not replace the entire project's include order based on this fragment. Wrappers do not solve ABI mismatches, missing import libraries, runtime dependencies or DLL search paths.

Compile a minimal include case and the actual third-party header in a temporary module to locate the polluting include, then check linking and loading. The original notes contain UE 5.5 errors and do not prove other versions passed. This addition excludes private paths and bulk raw logs without adding a plugin product description.
