# Loading Overhead of StaticMeshActor versus ISM/HISM

When a large UE scene loads for the first time, serializing many independent StaticMeshActors, initializing components, and registering them with the scene can all incur overhead. This article outlines how independent Actors and instanced meshes are organized and what to consider when merging manually.

## 1. Root Causes of Loading Stutters

### 1.1 Loading Overhead of Independent Actors

Suppose a scene has 500 identical trees. The traditional approach:

```cpp
// 场景中：500个AStaticMeshActor
for (int i = 0; i < 500; i++)
{
    AStaticMeshActor* Tree = SpawnActor<AStaticMeshActor>();
    Tree->SetStaticMesh(TreeMesh);
    Tree->SetActorLocation(Locations[i]);
}
```

**At load time, the engine must:**

1.  **Deserialize 500 UObjects** (each AStaticMeshActor + each UStaticMeshComponent)
2.  **Create 500 Components** (each requiring initialization and scene registration)
3.  **Build collision bodies 500 times** (each Component builds them independently, even with identical collision settings)
4.  **Register with the rendering system 500 times** (each Component submits rendering data independently)

**Core overhead:**

-   More independent Actors and components mean more serialization work
-   Component initialization involves many virtual-function calls and scene registrations
-   Collision bodies are built repeatedly, even with identical settings
-   Noncontiguous memory results in a low cache hit rate

### 1.2 Loading Advantages of ISM/HISM

After merging with HISM:

```cpp
// 合并后：1个AStaticMeshActor + 1个UHierarchicalInstancedStaticMeshComponent
UHierarchicalInstancedStaticMeshComponent* HISM = CreateDefaultSubobject<UHierarchicalInstancedStaticMeshComponent>();
HISM->SetStaticMesh(TreeMesh);

for (int i = 0; i < 500; i++)
{
    HISM->AddInstance(FTransform(Locations[i])); // 只添加Transform数据
}
```

**At load time, the engine must:**

1.  **Deserialize 1 UObject** (1 AStaticMeshActor)
2.  **Deserialize 1 HISM Component + 500 Transform matrices** (as a TArray)
3.  **Process the instanced component's collision data**
4.  **Register with the rendering system once** (submit instance data in a batch)
5.  **Build spatial organization data for instances** (used for instance culling)

**Key optimizations:**

-   ✅ **Far fewer UObjects**: 500 Actors → 1 Actor (substantially less serialization overhead)
-   ✅ **Far fewer Components**: 500 Components → 1 Component (substantially less initialization overhead)
-   ✅ **Transform-array serialization**: contiguous memory and efficient loading
-   ✅ **Centralized instance management**: the instanced component organizes mesh and transform data
-   ✅ **Batch organization of rendering data**: the instanced component manages multiple instances

## 2. Considerations for Manual Merging

### Workflow and Property Handling

In theory, you can optimize a scene by creating ISM/HISM manually:

1.  Create an Actor and add an `InstancedStaticMeshComponent` or `HierarchicalInstancedStaticMeshComponent`
2.  Add the Transforms of identical StaticMeshActors in the scene to ISM/HISM one at a time
3.  Delete the original independent Actors

**But this creates serious problems:**

**🔴 Disrupted workflow**

-   Artists can no longer place objects freely (instances must be added through code)
-   Adjusting positions requires editing the Transform array, which is highly inefficient
-   Standard editor tools cannot be used (move, rotate, duplicate)

**🔴 Error-prone property copying**

-   Mobility, collision settings, materials, rendering settings, and more must be copied manually
-   Missing any setting can cause abnormal behavior after merging, such as broken collision
-   Collision settings include responses for 32 channels, making mistakes very easy

**🔴 Huge workload in complex scenes**

-   Suppose a scene has 100 different Mesh types, each with dozens to hundreds of instances
-   You must create 100 ISM/HISM Actors and manually classify thousands of objects
-   Every scene adjustment requires another manual merge

**🔴 LevelInstances cannot be handled**

-   Breaking apart nested LevelInstances in a scene is extremely tedious
-   Breaking one apart may reveal more nesting, requiring repeated operations

## 3. Evaluating Merge Results

Instanced meshes can reduce the number of independent Actors and components. Actual loading time, memory usage, and runtime frame rate still need to be measured in the target scene. A reduction in object count cannot be treated as an equivalent proportional performance gain.

Before merging, check meshes, materials, mobility, and collision settings, and preserve a recoverable version of the scene.
