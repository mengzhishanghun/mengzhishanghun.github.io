UE: How to Create Dynamic Enums in UE
===

## Introduction

In UE project development, enums are among the most commonly used data types. However, traditional static enums have a critical problem: **their values are fixed at compile time and cannot be adjusted dynamically based on configuration**.

Imagine these scenarios:

- Your game has multiple AI types that need editor configuration, but you do not want to recompile the code every time you add an AI type
- Your level has multiple checkpoints that you want to add through a designer configuration table, but the enum values are hardcoded
- Your item system needs to read item types from an external configuration file, but C++ enums cannot be extended dynamically

This is the problem **dynamic enums** address: generating enum values dynamically at runtime while retaining type safety and editor friendliness.

This article introduces how dynamic enums work, shares my solution from a real project, and presents a ready-to-use plugin.

***

## What Is a Dynamic Enum?

### Pain Points of Traditional Static Enums

```cpp
// C++静态枚举：编译时固定
UENUM(BlueprintType)
enum class EAIType : uint8
{
    None,
    Soldier,
    Archer,
    Mage,
    Tank,
    MAX
};

```

**Problems:**

- ❌ Adding an AI type requires code changes and recompilation
- ❌ Designers cannot configure values independently and must rely on programmers
- ❌ Multiple projects cannot reuse the same enum definitions
- ❌ Every adjustment means waiting through a lengthy compile

### Limitations of Blueprint Enums

You might think: "Why not just use Blueprint enums? Designers can add values in the editor whenever they want."

Indeed, Blueprint enums can be configured in the editor, but they have a **critical problem**:

```cpp
// ❌ 无法在C++中使用蓝图枚举
void SpawnAI(/* 这里无法引用蓝图枚举类型 */)
{
    // C++代码无法直接访问蓝图枚举
    // 只能通过字符串或反射间接操作,失去类型安全
}

```

**Limitations of Blueprint enums:**

- ❌ **C++ cannot reference them** - Blueprint assets do not exist at compile time, so C++ code cannot use Blueprint enums as types
- ❌ **Loss of type safety** - They can only be manipulated indirectly through strings/integers, which is error-prone
- ❌ **Performance loss** - Runtime lookup and conversion are required, preventing compile-time optimization
- ❌ **Poor code readability** - Enum values are not visible in C++, making maintenance difficult

**Suitable scenarios:**

- ✅ Pure Blueprint projects with no C++ logic at all
- ❌ Projects requiring C++ and Blueprints to work together (the vast majority of commercial projects)

### The Dynamic Enum Approach (This Article)

```cpp
// 动态枚举：运行时从配置生成
UENUM(BlueprintType)
enum class EAIType : uint8
{
    None,    // 占位符：表示无效值
    MAX      // 占位符：表示边界
    // 中间的枚举值从配置文件动态生成!
};

```

**Comparison of the three approaches:**

| Feature | Static C++ enums | Blueprint enums | Dynamic enums (this article) |
| ------ | ------- | ---- | -------- |
| Configurable by designers | ❌ | ✅ | ✅ |
| Usable in C++ | ✅ | ❌ | ✅ |
| Usable in Blueprints | ✅ | ✅ | ✅ |
| Type safety | ✅ | ❌ | ✅ |
| Hot updates | ❌ | ✅ | ✅ |
| Performance | Optimal | Poorer | Optimal |

**Advantages of dynamic enums:**

- ✅ Designers can freely add enum values in editor settings
- ✅ Update enum contents without recompiling
- ✅ **Usable in both C++ and Blueprints while retaining type safety**
- ✅ Configuration tables, save files, and network transmission all use the same enum
- ✅ Compile-time optimization, with performance identical to static enums

## How Dynamic Enums Work

### UE's Enum Reflection System

UE exposes enums through its reflection system, with each enum represented by a `UEnum` object. The key discovery: **UE allows an enum's internal data to be modified at runtime**.

```cpp
// 获取枚举的反射对象
UEnum* EnumPtr = StaticEnum<EAIType>();

// 枚举内部用一个数组存储所有值
TArray<TPair<FName, int64>> EnumNameArray;

// 核心API:可以动态替换整个枚举!
EnumPtr->SetEnums(EnumNameArray, ECppForm::Namespaced);

```

**Implementation approach:**

1. Define an empty enum skeleton containing only `None` and `MAX`
2. Read enum values from configuration when the engine starts
3. Use `UEnum::SetEnums()` to dynamically fill the contents between `None` and `MAX`
4. The editor and Blueprints automatically recognize the new enum values

## Practical Example: Implementing Dynamic Enums from Scratch

Here is my implementation from an AI project. The code is concise but fully functional.

### Step 1: Define the Enum Skeleton

```cpp
// AIBlackboard.h
UENUM(BlueprintType)
enum class EAIFlowType : uint8
{
    None UMETA(DisplayName = "None")
};

UENUM(BlueprintType)
enum class EAIBlackboardBoolType : uint8
{
    None UMETA(DisplayName = "None")
};

```

Define only a `None` and wait for it to be populated at runtime.

### Step 2: Create a Configuration Class

```cpp
// AIHumanSettings.h
UCLASS(config = AIHuman, defaultconfig, DisplayName = "AIHuman Settings")
class UAIHumanSettings : public UDeveloperSettings
{
    GENERATED_BODY()
public:
    UPROPERTY(config, EditAnywhere, BlueprintReadOnly, Category = "Flow")
    TArray<FString> AIFlowTypeEnum;

    UPROPERTY(config, EditAnywhere, BlueprintReadOnly, Category = "Blackboard")
    TArray<FString> AIBlackboardBoolTypeEnum;

    // ... 更多枚举配置
};

```

Designers can control the enum values by editing these arrays in Project Settings.

### Step 3: Write the Core Initialization Function

```cpp
// AIHumanEngineSubsystem.h
static void DynamicInitEnum(UEnum* DynamicEnum, TArray<FString> EnumArray,
                           bool AddNone = true, bool AddMax = false)
{
    if(DynamicEnum == nullptr) return;

    TArray<TPair<FName, int64>> EnumNameArray;
    int64 CurEnumIndex = 0;

    // 添加None值
    if(AddNone)
    {
        EnumNameArray.Emplace(TPairInitializer<FName, int64>(
            FName(*DynamicEnum->GenerateFullEnumName(*FString("None"))),
            CurEnumIndex++));
    }

    // 添加配置中的枚举值
    for(auto It : EnumArray)
    {
        if(It.IsEmpty()) continue;
        EnumNameArray.Emplace(TPairInitializer<FName, int64>(
            FName(*DynamicEnum->GenerateFullEnumName(*It)),
            CurEnumIndex++));
    }

    // 添加Max值(可选)
    if(AddMax)
    {
        EnumNameArray.Emplace(TPairInitializer<FName, int64>(
            FName(*DynamicEnum->GenerateFullEnumName(*FString("Max"))),
            CurEnumIndex++));
    }

    // 替换枚举内容
    DynamicEnum->SetEnums(EnumNameArray, DynamicEnum->GetCppForm());
}

```

### Step 4: Initialize in an Engine Subsystem

```cpp
// AIHumanEngineSubsystem.cpp
void UAIHumanEngineSubsystem::Initialize(FSubsystemCollectionBase& Collection)
{
    Super::Initialize(Collection);

    UAIHumanSettings* Settings = GetMutableDefault<UAIHumanSettings>();

    // 初始化所有动态枚举
    DynamicInitEnum(StaticEnum<EAIFlowType>(), Settings->AIFlowTypeEnum);
    DynamicInitEnum(StaticEnum<EAIBlackboardBoolType>(), Settings->AIBlackboardBoolTypeEnum);

    // 监听配置变化,编辑器中修改后立即生效
    Settings->OnSettingChanged().AddLambda([](UObject* Object, FPropertyChangedEvent& PropertyChangedEvent)
    {
        UAIHumanSettings const* Settings = GetDefault<UAIHumanSettings>();

        if(PropertyChangedEvent.GetPropertyName() == "AIFlowTypeEnum")
        {
            DynamicInitEnum(StaticEnum<EAIFlowType>(), Settings->AIFlowTypeEnum);
        }
        // ... 其他枚举的热更新
    });
}

```

**Key points:**

- Use `UEngineSubsystem` rather than `EditorSubsystem` so it also works in packaged builds
- `OnSettingChanged()` listens for configuration changes to enable hot updates in the editor

### Demonstration

The designer configures the following in **Project Settings -> AIHuman Settings**:

```
AIFlowTypeEnum:
  - "巡逻"
  - "追击"
  - "撤退"
  - "警戒"

```

After saving, the enum `EAIFlowType` automatically becomes:

```cpp
enum class EAIFlowType : uint8
{
    None,
    巡逻,    // 动态生成
    追击,    // 动态生成
    撤退,    // 动态生成
    警戒,    // 动态生成
};

```

The dropdown in Blueprints refreshes immediately, without restarting the editor!

## Limitations of This Approach

Although the implementation above is usable, I found several issues in real projects:

### 1. Too Much Boilerplate

For every new enum, you have to:

- Add a `TArray<FString>` property to the configuration class
- Call `DynamicInitEnum()` during subsystem initialization
- Write repetitive if checks in `OnSettingChanged()`

Ten enums require 30 lines of nearly identical code, which is error-prone and difficult to maintain.

### 2. Missing Robustness Checks

- No deduplication: entering "Patrol" twice in the configuration generates duplicate enum entries
- No whitespace filtering: "Soldier" and "Soldier " are treated as different values
- No boundary checks: None/MAX may be overwritten
- No error logging: problems are difficult to troubleshoot

### 3. No Support for Complex Scenarios

- Cannot customize the names of None/MAX (for example, using Begin/End)
- Cannot bind multiple configuration arrays to different ranges of one enum
- Cannot dynamically switch configuration sources at runtime

### 4. Difficult to Reuse Across Projects

The code has to be copied and pasted into every project, and updates are difficult to synchronize when versions differ.

## A Ready-to-Use Solution

To address these issues, I developed the **[SimpleAutoEnum | Fab](https://www.fab.com/zh-cn/listings/2d104382-60b1-4da6-86c6-ed93997f9c0a)** plugin. It retains the underlying principle while providing a complete engineering solution.

### Core Features

#### 1. Bind with a Single Macro Line

```cpp
// 传统方式:3个地方写代码
// 配置类 -> 手动调用初始化 -> 手动监听变化

// SimpleAutoEnum:一行搞定
SIMPLE_BIND_ENUM_TO_CONFIG(EAIType, None, MAX, UMySettings, AITypeList)

```

**How it works:**

- The expanded macro creates a static initializer that registers automatically when the engine starts
- No manual code is needed in the subsystem
- An anonymous namespace prevents symbol conflicts

#### 2. Comprehensive Data Validation

```cpp

["Soldier", "Archer", "Soldier"] → ["Soldier", "Archer"]

// 过滤空值和空格
["", " ", "Mage "] → ["Mage"]

// 保护None/MAX
["None", "Soldier", "MAX"] → ["Soldier"]  // None和MAX不会被覆盖

```

#### 3. Flexible Boundary Definitions

```cpp

{
    None,
```

### Practical Usage Examples

The plugin supports three common usage patterns to meet different needs.

#### Example 1: Standard Usage - One-to-One Binding

The most common pattern: one enum bound to one configuration array.

```cpp
// 1. 定义枚举框架
UENUM(BlueprintType)
enum class EWeaponType : uint8
{
    None,
    MAX
};

// 2. 创建配置类
UCLASS(Config=Game, DefaultConfig, meta=(DisplayName="Game Settings"))
class UMyGameSettings : public UDeveloperSettings
{
    GENERATED_BODY()
public:
    UPROPERTY(Config, EditAnywhere, Category="Weapons")
    TArray<FString> WeaponsList;
};

// 3. 绑定枚举
SIMPLE_BIND_ENUM_TO_CONFIG(EWeaponType, None, MAX, UMyGameSettings, WeaponsList)

```

**Configuration:**

```
WeaponsList: ["剑", "斧", "弓", "法杖"]

```

**Result:**

```cpp
EWeaponType::None, 剑, 斧, 弓, 法杖, EWeaponType::MAX

```

#### Example 2: Range Binding - Combining Multiple Arrays

Bind multiple configuration arrays to different ranges of one enum, suitable for managing categories.

```cpp
// 定义带有多个边界的枚举
UENUM(BlueprintType)
enum class ECombinedWeapons : uint8
{
    None            UMETA(DisplayName = "None"),
    PrimaryEnd      UMETA(DisplayName = "--- Primary End ---"),
    AllWeaponsEnd   UMETA(DisplayName = "--- All End ---")
};

// 绑定主武器到第一个范围
SIMPLE_BIND_ENUM_TO_CONFIG(ECombinedWeapons, None, PrimaryEnd, UMyGameSettings, PrimaryWeaponsList)
// 绑定副武器到第二个范围
SIMPLE_BIND_ENUM_TO_CONFIG(ECombinedWeapons, PrimaryEnd, AllWeaponsEnd, UMyGameSettings, SecondaryWeaponsList)

```

**Configuration:**

```
PrimaryWeaponsList: ["长剑", "战斧"]
SecondaryWeaponsList: ["匕首", "手枪"]

```

**Result:**

```cpp
None, 长剑, 战斧, PrimaryEnd, 匕首, 手枪, AllWeaponsEnd

```

**Suitable scenarios:**

- Weapon systems (primary/secondary/special weapons)
- Skill categories (active/passive/ultimate skills)
- Item categories (consumables/equipment/materials)

#### Example 3: Shared Array - Multiple Enums Sharing One Array

Multiple enums use the same configuration array to keep their categories consistent.

```cpp
// 品质等级枚举(用于UI显示)
UENUM(BlueprintType)
enum class EUIQuality : uint8
{
    None,
    Max

SIMPLE_BIND_ENUM_TO_CONFIG(EUIQuality, None, Max, UMyGameSettings, QualityLevelsArray)

// 物品品质枚举(用于道具系统)
```

**Configuration:**

## Conclusion

Dynamic enums address the core pain point of traditional static enums: **configuration-driven values vs hardcoded values**.

**Core value:**

- Designers configure values independently, without programmer involvement
- Real-time editor updates improve iteration efficiency
- Retain type safety and avoid hardcoded strings
- Consistent usage across Blueprints/C++/configuration

From principles to practical implementation, this article demonstrates how to build dynamic enums from scratch and shares an engineered plugin solution. For projects requiring many configurable enums, **SimpleAutoEnum** can significantly reduce boilerplate and improve the development experience.
