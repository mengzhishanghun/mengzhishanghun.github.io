# Creating Dynamic Enums in UE

## Introduction

Enums are one of the most commonly used data types in UE development. Traditional static enums have a critical limitation: **their values are fixed at compile time and cannot adjust dynamically to configuration**.

Imagine these scenarios:

-   Your game has multiple AI types to configure in the editor, but you do not want to recompile whenever you add one
-   Your level has multiple checkpoints that designers want to add to a configuration table, but enum values are hardcoded
-   Your item system must read item types from an external configuration file, but C++ enums cannot expand dynamically

This is what **dynamic enums** address: generating enum values dynamically at runtime while retaining type safety and editor usability.

This article explains the implementation principles, configuration-binding examples, and boundaries that must be handled.

* * *

## What Is a Dynamic Enum?

### Pain Points of Traditional Static Enums

```cpp
// C++静态枚举：编译时固定
UENUM(BlueprintType)
enum class EAIType : uint8
{
    None,
    Soldier,
    Archer,
    Mage,
    Tank,
    MAX
};
```

**Problems:**

-   ❌ Adding an AI type requires code changes and recompilation
-   ❌ Designers cannot configure it independently and depend on programmers
-   ❌ The same enum definition cannot be reused across multiple projects
-   ❌ Every adjustment requires a long compilation wait

### Limitations of Blueprint Enums

You might ask: “Why not just use a Blueprint enum? Designers can add values in the editor whenever they want.”

Indeed, Blueprint enums can be configured in the editor, but they have a **critical problem**:

```cpp
// ❌ 无法在C++中使用蓝图枚举
void SpawnAI(/* 这里无法引用蓝图枚举类型 */)
{
    // C++代码无法直接访问蓝图枚举
    // 只能通过字符串或反射间接操作,失去类型安全
}
```

**Blueprint enum limitations:**

-   ❌ **Cannot be referenced in C++**—Blueprint assets do not exist at compile time, so C++ cannot use a Blueprint enum as a type
-   ❌ **Loss of type safety**—indirect manipulation through strings/integers is error-prone
-   ❌ **Performance loss**—runtime lookup and conversion are required, preventing compile-time optimization
-   ❌ **Poor code readability**—enum values are invisible in C++, making maintenance difficult

**Use cases:**

-   ✅ Blueprint-only projects with no C++ logic
-   ❌ Projects combining C++ and Blueprints (most commercial projects)

### The Dynamic Enum Approach in This Article

```cpp
// 动态枚举：运行时从配置生成
UENUM(BlueprintType)
enum class EAIType : uint8
{
    None,    // 占位符：表示无效值
    MAX      // 占位符：表示边界
    // 中间的枚举值从配置文件动态生成!
};
```

**Comparison of the three approaches:**

| Feature | Static C++ enum | Blueprint enum | Dynamic enum (this article) |
| --- | --- | --- | --- |
| Designer-configurable | ❌ | ✅ | ✅ |
| Usable in C++ | ✅ | ❌ | ✅ |
| Usable in Blueprints | ✅ | ✅ | ✅ |
| Type safety | ✅ | ❌ | ✅ |
| Hot updates | ❌ | ✅ | ✅ |
| Performance | Best | Lower | Best |

**Advantages of dynamic enums:**

-   ✅ Designers can freely add enum values in editor settings
-   ✅ Hot-update enum contents without recompiling
-   ✅ **Usable in both C++ and Blueprints while retaining type safety**
-   ✅ Configuration tables, saves, and network transmission use the same enum
-   ✅ Compile-time optimization with performance equal to static enums

## How Dynamic Enums Work

### UE's Enum Reflection System

UE exposes enums through its reflection system, with each enum represented by a `UEnum` object. The key discovery is that **UE allows the internal enum data to be modified at runtime**.

```cpp
// 获取枚举的反射对象
UEnum* EnumPtr = StaticEnum<EAIType>();

// 枚举内部用一个数组存储所有值
TArray<TPair<FName, int64>> EnumNameArray;

// 核心API:可以动态替换整个枚举!
EnumPtr->SetEnums(EnumNameArray, ECppForm::Namespaced);
```

**Implementation approach:**

1.  Define an empty enum framework containing only `None` and `MAX`
2.  Read enum values from configuration when the engine starts
3.  Use `UEnum::SetEnums()` to fill the values between `None` and `MAX` dynamically
4.  The editor and Blueprints recognize the new values automatically

## Practical Example: Implementing a Dynamic Enum from Scratch

The following is my implementation in an AI project. The code is concise but functionally complete.

### Step One: Define the Enum Framework

```cpp
// AIBlackboard.h
UENUM(BlueprintType)
enum class EAIFlowType : uint8
{
    None UMETA(DisplayName = "None")
};

UENUM(BlueprintType)
enum class EAIBlackboardBoolType : uint8
{
    None UMETA(DisplayName = "None")
};
```

Define only `None` and wait for runtime population.

### Step Two: Create the Configuration Class

```cpp
// AIHumanSettings.h
UCLASS(config = AIHuman, defaultconfig, DisplayName = "AIHuman Settings")
class UAIHumanSettings : public UDeveloperSettings
{
    GENERATED_BODY()
public:
    UPROPERTY(config, EditAnywhere, BlueprintReadOnly, Category = "Flow")
    TArray<FString> AIFlowTypeEnum;

    UPROPERTY(config, EditAnywhere, BlueprintReadOnly, Category = "Blackboard")
    TArray<FString> AIBlackboardBoolTypeEnum;

    // ... 更多枚举配置
};
```

Designers edit these arrays in Project Settings to control enum values.

### Step Three: Write the Core Initialization Function

```cpp
// AIHumanEngineSubsystem.h
static void DynamicInitEnum(UEnum* DynamicEnum, TArray<FString> EnumArray,
                           bool AddNone = true, bool AddMax = false)
{
    if(DynamicEnum == nullptr) return;

    TArray<TPair<FName, int64>> EnumNameArray;
    int64 CurEnumIndex = 0;

    // 添加None值
    if(AddNone)
    {
        EnumNameArray.Emplace(TPairInitializer<FName, int64>(
            FName(*DynamicEnum->GenerateFullEnumName(*FString("None"))),
            CurEnumIndex++));
    }

    // 添加配置中的枚举值
    for(auto It : EnumArray)
    {
        if(It.IsEmpty()) continue;
        EnumNameArray.Emplace(TPairInitializer<FName, int64>(
            FName(*DynamicEnum->GenerateFullEnumName(*It)),
            CurEnumIndex++));
    }

    // 添加Max值(可选)
    if(AddMax)
    {
        EnumNameArray.Emplace(TPairInitializer<FName, int64>(
            FName(*DynamicEnum->GenerateFullEnumName(*FString("Max"))),
            CurEnumIndex++));
    }

    // 替换枚举内容
    DynamicEnum->SetEnums(EnumNameArray, DynamicEnum->GetCppForm());
}
```

### Step Four: Initialize in an Engine Subsystem

```cpp
// AIHumanEngineSubsystem.cpp
void UAIHumanEngineSubsystem::Initialize(FSubsystemCollectionBase& Collection)
{
    Super::Initialize(Collection);

    UAIHumanSettings* Settings = GetMutableDefault<UAIHumanSettings>();

    // 初始化所有动态枚举
    DynamicInitEnum(StaticEnum<EAIFlowType>(), Settings->AIFlowTypeEnum);
    DynamicInitEnum(StaticEnum<EAIBlackboardBoolType>(), Settings->AIBlackboardBoolTypeEnum);

    // 监听配置变化,编辑器中修改后立即生效
    Settings->OnSettingChanged().AddLambda([](UObject* Object, FPropertyChangedEvent& PropertyChangedEvent)
    {
        UAIHumanSettings const* Settings = GetDefault<UAIHumanSettings>();

        if(PropertyChangedEvent.GetPropertyName() == "AIFlowTypeEnum")
        {
            DynamicInitEnum(StaticEnum<EAIFlowType>(), Settings->AIFlowTypeEnum);
        }
        // ... 其他枚举的热更新
    });
}
```

**Key points:**

-   Use `UEngineSubsystem` rather than `EditorSubsystem`, so it also works after packaging
-   `OnSettingChanged()` listens for configuration changes to enable editor hot updates

### Demonstration

Designers configure the following in **Project Settings → AIHuman Settings**:

```
AIFlowTypeEnum:
  - "巡逻"
  - "追击"
  - "撤退"
  - "警戒"
```

After saving, `EAIFlowType` automatically becomes:

```cpp
enum class EAIFlowType : uint8
{
    None,
    巡逻,    // 动态生成
    追击,    // 动态生成
    撤退,    // 动态生成
    警戒,    // 动态生成
};
```

The Blueprint dropdown refreshes immediately without restarting the editor!

## Limitations of This Approach

Although the implementation is usable, I found several issues in real projects:

### 1\. Too Much Boilerplate

For every new enum, you must:

-   Add a `TArray<FString>` property to the configuration class
-   Call `DynamicInitEnum()` in subsystem initialization
-   Write repeated if checks in `OnSettingChanged()`

Ten enums require 30 almost identical lines, making errors likely and maintenance difficult.

### 2\. Missing Robustness Checks

-   No deduplication: entering “Patrol” twice produces duplicate enum values
-   No whitespace filtering: “Soldier” and “Soldier ” are treated as different values
-   No boundary checks: None/MAX may be overwritten
-   No error logs: problems are hard to diagnose

### 3\. Unsupported Complex Scenarios

-   Cannot customize the names of None/MAX (for example, Begin/End)
-   Cannot bind multiple configuration arrays to different ranges of one enum
-   Cannot switch configuration sources dynamically at runtime

### 4\. Difficult Cross-Project Reuse

Every project must copy and paste this code, and differing versions make updates difficult to synchronize.

* * *

## Summary

Dynamic enums combine configuration data with enum reflection to reduce some hardcoding. This article preserves the implementation from the configuration class and enum initialization through engine-subsystem calls. Array bounds, empty strings, duplicate values, and cross-project reuse still require separate handling.
