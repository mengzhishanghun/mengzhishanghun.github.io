# Data Serialization and Byte Conversion in Blueprints

## Introduction

Network communication, data persistence, and interaction with external programs are common requirements in UE projects. Whether you send structured data over UDP/TCP or serialize game state into binary storage, one core operation is unavoidable: **converting data into a byte array**.

However, this is not straightforward in Blueprints:

-   There are no native byte-conversion nodes; int32, float, and double cannot directly become `TArray<uint8>`
-   Struct serialization is even harder, and CustomThunk has too high a barrier for Blueprint-only users
-   UE's built-in `FJsonObjectConverter` suffers serious floating-point precision loss during serialization
-   Encoding formats may not match when exchanging data with external Python, C#, or C++ programs

## Primitive Types and Byte Arrays

```cpp
// 以 int32 为例，直接内存拷贝
void ByteConverter::IntToBytes(int32 Value, TArray<uint8>& OutBytes)
{
    OutBytes.SetNumUninitialized(sizeof(int32));
    FMemory::Memcpy(OutBytes.GetData(), &Value, sizeof(int32));
}
```

The example uses `FMemory::Memcpy` to copy the memory representation of primitive types. String conversion uses UTF-8 and handles the Null Terminator automatically for cross-platform compatibility.

## Accepting Generic Structs in Blueprints

**Key technique: CustomThunk**

Blueprints cannot pass generic structs directly. `CustomThunk` + `CustomStructureParam` can provide a generic struct parameter:

```cpp
UFUNCTION(BlueprintPure, CustomThunk,
    meta = (CustomStructureParam = "Struct", DisplayName = "Struct To Bytes"),
    Category = "SimpleByteConversion|Struct")
static void StructToBytes(const int32& Struct, TArray<uint8>& Bytes);
DECLARE_FUNCTION(execStructToBytes);
```

This means you can plug **any custom struct** directly into a Blueprint node, identify its type in the execution function, and serialize it.

## JSON Field Names and Floating-Point Output

UE's default JSON serialization has two problems:

1.  **Field names include internal engine suffixes** (such as `MyField_5_A3B2C1D4`)
2.  **Floating-point precision is lost** (float retains only 6 significant digits)

The original article addresses these with a custom `FExactPrintPolicy` and field-name cleanup:

```cpp
// 高精度输出：float 保留9位，double 保留17位
template <typename CharT>
struct FExactPrintPolicy : TCondensedJsonPrintPolicy<CharT>
{
    static void WriteFloat(FArchive* Stream, float V)
    {
        FString S = FString::Printf(TEXT("%.9f"), V);
        TCondensedJsonPrintPolicy<CharT>::WriteString(Stream, S);
    }
    static void WriteDouble(FArchive* Stream, double V)
    {
        FString S = FString::Printf(TEXT("%.17g"), V);
        TCondensedJsonPrintPolicy<CharT>::WriteString(Stream, S);
    }
};
```

The resulting JSON has clean field names and full numerical precision, and can be parsed directly by external programs such as Python and C#.
