UE: How to Fix Child Blueprint Component Property Changes Affecting the Parent
===

> © [mengzhishanghun](https://github.com/mengzhishanghun) · Original article\
> &#x20;First published on [Cnblogs](https://www.cnblogs.com/mengzhishanghun) · Unauthorized reproduction prohibited

***

## Introduction

If you have used Blueprint inheritance in a complex UE project, you have probably run into this strange behavior:

- **The component's Cut / Delete menu options are grayed out in the parent Blueprint** — it clearly belongs to the parent, yet you cannot delete it
- **Changing any property of that component in a child Blueprint (even just checking a bool) writes the change back to the parent Blueprint** — child changes are no longer isolated, and the inheritance chain becomes polluted in both directions

If this has happened to you, you probably know how hopeless it feels. You can spend ages investigating without finding a clue, while online suggestions range wildly from rebuilding the Blueprint to changing its parent or deleting and re-adding components. Many of these also break other parts of the inheritance chain.

**SimpleBPInheritFix is a plugin specifically for this bug**. Right-click any affected Blueprint to fix it in one step: it automatically scans, checks out, and repairs all damaged components throughout the inheritance chain. It leaves every other field untouched and makes very conservative changes.

***

## 1. What Exactly Is This Bug?

### 1.1 Root Cause

UE's `UActorComponent` has a field named `CreationMethod` that describes how a component was created:

| Enum value | Meaning |
| -------------------------- | ---------------------------------------- |
| `Native` | A component created in a C++ constructor |
| `SimpleConstructionScript` | A component added through the Blueprint editor's Components panel (**a normal Blueprint component**) |
| `UserConstructionScript` | Dynamically created in ConstructionScript nodes |
| `Instance` | Added to a specific Actor instance at runtime (**should not appear in a Blueprint template**) |

**The essence of the bug**: for a Blueprint's component template (`ComponentTemplate`), certain unknown operations incorrectly set its `CreationMethod` to `Instance`. Once it becomes `Instance`, the UE editor considers it something other than a "component defined by the Blueprint itself," so:

- The parent Blueprint's Cut / Delete menu items take a different branch and become grayed out
- Property changes in child classes are treated as "instance-level changes" and written back to the parent template (instead of creating an override in the child)

### 1.2 What Triggers It?

Certain sequences of operations inside the UE editor (such as Blueprint duplication, renaming, and reparenting in a particular order) can trigger it unexpectedly. The exact sequence is difficult to reproduce consistently, but **once it happens, it persists** and does not heal itself after saving.

### 1.3 Why Manual Repair Is Awkward

In theory, you just need to change `CreationMethod` back to `SimpleConstructionScript`, but there are several pitfalls in practice:

1. **The component may appear in both SCS nodes and ICH records** (see Section 3 below), and both locations must be changed
2. **Several Blueprint levels in the inheritance chain may be affected at once**, so fixing only one is ineffective
3. **Child Blueprints** (those that use the current Blueprint as their parent) may also be polluted and need repairing together
4. **Files under source control are read-only by default** and must be checked out individually

You cannot change this field by clicking around in the Details panel. You have to write a script and know UE's internal Blueprint structures well enough.

***

## 2. Core Plugin Features

### 2.1 One-click Trigger

Right-click any **Actor Blueprint** in the Content Browser and select **Component Repair → Fix Inheritance Pollution**.

It does not matter which Blueprint you choose as the anchor — whether a parent, the Blueprint itself, or a child, the plugin scans the entire inheritance chain all the way through.

### 2.2 Full-chain Scanning

The plugin uses two mechanisms to scan the entire inheritance chain:

- **Upward**: follows the anchor Blueprint's `ParentClass` level by level to the top, collecting all parent Blueprints
- **Downward**: uses UE's `AssetRegistry.GetDerivedClassNames()` to obtain all derived Blueprint classes

After merging these two sets and removing duplicates, the result is the complete scope to inspect and repair in this run.

### 2.3 Both SCS and ICH Paths Covered

Inherited component information for Blueprints exists in two locations, and both must be checked:

- **SCS nodes** (`SimpleConstructionScript.AllNodes`): components defined directly by the Blueprint
- **ICH records** (`InheritableComponentHandler.CreateRecordIterator()`): records of overrides a child Blueprint makes to components inherited from its parent

The plugin scans both locations for every Blueprint, finding and repairing any record with `CreationMethod == Instance`.

### 2.4 Automatic Source Control Integration

Before making changes, it automatically uses UE's `ISourceControlModule` to check out affected `.uasset` files:

- **Perforce**: `p4 edit`
- **Git LFS**: requests an LFS lock
- **SVN**: `svn lock`
- **Git (without LFS)**: essentially a no-op, since the files are already writable
- **No source control**: skips the entire checkout stage

***

## 3. Repair Process (5 Stages)

The plugin proceeds through 5 stages. Each is clearly labeled in the Output Log's `LogSBIF` channel for easier troubleshooting:

| Stage | Action |
| ----------------------- | -------------------------------------------------------------- |
| 1. **GatherChain** | Collect the inheritance chain (parents + self + children) |
| 2. **ScanChain** | Scan every Blueprint's SCS + ICH to find all records with `CreationMethod=Instance` |
| 3. **CheckOutFindings** | Check out the relevant uassets through source control |
| 4. **ApplyFindings** | Flip `CreationMethod` from `Instance` to `SimpleConstructionScript` |
| 5. **MarkDirty** | Mark modified Blueprints as dirty and prompt the user to save them manually |

If the scan finds no damaged nodes (stage 2 reports 0), the plugin exits immediately and reports "No repair needed" — **it does not touch any files**.

***

## 4. Usage Steps

1. Install the plugin and compile successfully
2. Right-click any affected Actor Blueprint in the Content Browser
3. Select **Component Repair → Fix Inheritance Pollution**
4. Open the Output Log and filter for `LogSBIF` to inspect execution
5. When the editor displays a save dialog, **save the Blueprints marked as dirty** to finish

## 5. Frequently Asked Questions

### The scan finds 0 records, but there really is pollution?

It is probably a problem outside this plugin's coverage (a rare situation). Copy the complete `LogSBIF` log into the comments on the Fab product page to help with troubleshooting.

### What if CheckOut fails?

The plugin still completes the in-memory repair, but you need to handle checkout manually before saving. Common causes:

- The file is locked by someone else
- The source control server is unreachable
- The workspace mapping does not include the file

Resolve checkout manually first, then return to UE to save.

### Could it damage normal components?

No. The repair logic **only flips the single field `CreationMethod`** (`Instance → SimpleConstructionScript`) and leaves every other property untouched. This field should never be `Instance` for a Blueprint component template, so flipping it back simply restores the correct state.

### Does choosing the wrong anchor Blueprint matter?

No. Whether you right-click a parent, the Blueprint itself, or a child, the plugin scans the entire chain upward and downward, with exactly the same result.

### Can I use it without Perforce?

- **Git**: checkout is essentially a no-op, since files are already writable
- **Git LFS**: automatically requests an LFS lock
- **SVN**: executes `svn lock`
- **No source control**: skips the entire checkout stage and proceeds directly to repair

***

## 6. Limitations

- Only handles the specific component anomaly covered by this plugin (`CreationMethod=Instance` pollution); other types of Blueprint problems are outside its scope
- Components dynamically generated in the Construction Script are not scanned (they do not use SCS/ICH in the first place)
- Only supports Actor Blueprints (non-Actor Blueprints do not have this issue)

***

## 7. Getting the Plugin

Search for **SimpleBPInheritFix** on Fab.

- Supported: UE 5.2+
- Platforms: Windows / macOS / Linux
