# Component State Contamination in Blueprint Inheritance and a Repair Approach

## Introduction

If you have built a complex UE project with Blueprint inheritance, you have probably encountered this strange behavior:

-   **The component's Cut / Delete menu is grayed out in the parent Blueprint**—even though the component belongs to the parent itself, it cannot be deleted
-   **Changing any property of that component in a child Blueprint—even a bool checkbox—writes the change back to the parent Blueprint**—child changes are no longer isolated, and the inheritance chain becomes contaminated

## 1. What Is This Bug?

### 1.1 Root Cause

UE's `UActorComponent` has a `CreationMethod` field describing how the component was created:

| Enum value | Meaning |
| --- | --- |
| `Native` | A component created in a C++ constructor |
| `SimpleConstructionScript` | A component added through the Blueprint editor's Components panel (**a normal Blueprint component**) |
| `UserConstructionScript` | Dynamically created in ConstructionScript nodes |
| `Instance` | A component added to a specific Actor instance at runtime (**should not appear in a Blueprint template**) |

**The essence of the bug**: certain unknown operations incorrectly set the `CreationMethod` of a Blueprint's component template (`ComponentTemplate`) to `Instance`. Once this happens, the UE editor no longer considers it a component defined by the Blueprint itself, so:

-   The parent Blueprint's Cut / Delete menu takes a different branch and becomes disabled
-   Child property changes are treated as instance-level edits and written back to the parent template, instead of producing an override in the child

### 1.2 What Triggers It?

Certain sequences of editor operations—such as copying, renaming, or changing Blueprint parents in a particular order—can trigger it accidentally. The exact reproduction path is difficult to reproduce consistently, but **once it occurs, it persists** and does not heal after saving.

### 1.3 Why Manual Repair Is Difficult

In theory, changing `CreationMethod` back to `SimpleConstructionScript` is enough, but there are several pitfalls:

1.  **The component may exist in both SCS nodes and ICH records** (explained below), and both locations must be changed
2.  **Multiple Blueprints along the inheritance chain may be affected**, so fixing just one does not help
3.  **Child Blueprints** that use the current Blueprint as their parent may also be contaminated and need repair
4.  **Files under source control are read-only by default** and must be checked out individually

You cannot edit this field simply by clicking in the Details panel. You need a script and sufficient knowledge of UE's internal Blueprint structures.

## 2. Scan Scope

### Scanning the Inheritance Chain

To scan the entire chain, collect Blueprints in two directions:

-   **Upward**: follow the anchor Blueprint's `ParentClass` to the top, collecting all Blueprints used as parents
-   **Downward**: use UE's `AssetRegistry.GetDerivedClassNames()` to obtain all derived Blueprint classes

Merge and deduplicate these two sets to obtain the complete scope to inspect and repair.

### Component Records in SCS and ICH

Inherited Blueprint component information exists in two places, both of which must be checked:

-   **SCS nodes** (`SimpleConstructionScript.AllNodes`): components directly defined by the Blueprint
-   **ICH records** (`InheritableComponentHandler.CreateRecordIterator()`): records of overrides made by child Blueprints to inherited parent components

Scan both locations in each Blueprint for records where `CreationMethod == Instance`.

## 3. Repair Workflow

First collect the inheritance chain and identify affected components, then handle source-control checkout, field changes, and saving.

| Stage | Action |
| --- | --- |
| 1\. **GatherChain** | Collect the inheritance chain (parents + self + children) |
| 2\. **ScanChain** | Scan each Blueprint's SCS + ICH for every record with `CreationMethod=Instance` |
| 3\. **CheckOutFindings** | Check out the affected uassets through source control |
| 4\. **ApplyFindings** | Change `CreationMethod` from `Instance` to `SimpleConstructionScript` |
| 5\. **MarkDirty** | Mark changed Blueprints dirty and prompt the user to save manually |

## 4. Applicability

This discussion concerns abnormal CreationMethod values in Actor Blueprint component templates. It does not cover other Blueprint failures. Components created dynamically in Construction Script require separate assessment; the same repair logic cannot be applied directly.
