# Letting AI Modify DataAssets Directly

## Introduction

I wanted to let AI handle complex DataAsset edits: read existing configuration, change basic fields, nested structs, and container data through JSON, then synchronize it back to UE in real time. This reduces manual data transfer whether an LLM generates level configuration or a reinforcement-learning system adjusts balance values.

In UE, skill tables, character attributes, loot tables, and AI behavior parameters are often stored in DataAssets. A DataAsset is a UE-serialized binary file (.uasset), which external tools cannot process directly. AI-generated or modified values therefore still need to be entered into the editor manually, a step that consumes time on each iteration.

I use JSON as an intermediate format so AI can read and write the data as text. While the UE editor is running, the plugin monitors JSON changes and writes them back to DataAssets in real time, supporting basic types and most structs. Implementing this requires property conversion, change monitoring, and asset writes. Export, file monitoring, and asset updates run automatically without manual import or export; the initial scan at startup displays synchronization progress. This article records the problems encountered when implementing two-way synchronization. For the tool's purpose and use cases, see the [AIDataAsset overview](/en/works/ai-data-asset/).

## Why JSON?

DataAssets and external tools need an intermediate format they can both handle. CSV, XML, and YAML are options; I chose JSON mainly because:

- It has native support in almost every programming language and AI framework
- It is human-readable and easy to debug
- Text diffs make individual fields available for reviewing data changes
- Its flexible structure can express common nested UE data types

JSON is stored in the project's `Saved/AIDataAsset/` directory by default as an intermediate file for background synchronization, and normally should not be tracked in version control. To track field changes in JSON, ask the AI tool to change the plugin's `JSON Output Directory` configuration to a location within the project that should be tracked, then add the JSON files to version control.

## UE's Built-in JSON Serialization

UE's built-in JSON utility, `FJsonObjectConverter`, provides two main functions:

- **UStructToJsonObject**: serializes any UStruct, including all UPROPERTY fields of a DataAsset, into an FJsonObject
- **JsonObjectToUStruct**: deserializes an FJsonObject back into a UStruct

It handles most UPROPERTY types: primitives, FString, FName, enums, nested UStructs, TArray, TMap, TSet, and even soft references (FSoftObjectPath).

**If you only need one-way, manually triggered export or import, this is enough.** An editor tool button can export JSON; after AI edits it, another click imports it. This is entirely workable.

Automatically updating JSON when a DataAsset changes, and updating the DataAsset when external JSON changes, requires two-way synchronization.

## Pitfalls in Two-Way Synchronization

Automatic two-way synchronization raised the following issues beyond format conversion.

### Loss of Floating-Point Precision

Floating-point output formatting is easy to overlook, but directly affects exported values.

UE's default JSON serialization does not format floating-point values with enough precision. A value set to `0.3` in the editor may become `0.30000000000000004` after export. This precision drift is unacceptable for sensitive game parameters such as damage multipliers, probability weights, and physics parameters.

The solution is a custom JSON PrintPolicy. Use `%.9f` for float (9 decimal places) and `%.17g` for double (17 significant digits, the full precision of IEEE 754 double precision). This ensures values remain identical after a DataAsset → JSON → DataAsset round trip.

### Inconsistent Capitalization of Property Names

`FJsonObjectConverter` lowercases the first letter of property names during serialization: `MaxHealth` in the editor becomes `maxHealth` in the export.

This is more than cosmetic. AI sees `maxHealth` in JSON and `MaxHealth` in the editor; mismatched names make the data harder to understand. Worse, if AI writes `MaxHealth` into JSON using the editor's name, deserialization may fail to match it.

The solution is to recursively traverse all JSON fields after export and restore the uppercase initial; apply the reverse conversion before import.

### Trigger Loops

Two-way synchronization can keep triggering along this path:

1. The user changes a DataAsset in the editor
2. A listener detects the change and exports it to JSON
3. The file system detects a JSON change
4. A listener imports that change back into the DataAsset
5. The process returns to step 2 and repeats indefinitely

The implementation uses two safeguards:

- **Synchronization flag `bIsSyncing`**: set to true during startup synchronization and directory-change handling. Asset property, addition, deletion, renaming, and package-reload callbacks return while synchronization is active, preventing another export during import.
- **Self-written path set `PendingSelfChanges`**: after export actually writes a file, its normalized path is recorded. When directory monitoring receives a notification for that path, it removes the marker and skips that notification, rather than treating its own export as an external edit.

File-system notifications may arrive after the synchronization flag has been reset, so path tracking is also needed. Before export, the existing file is compared with the newly generated JSON text. Before import, the current asset's serialized text is compared with the file contents. An exact string match skips processing. This compares text, not JSON semantics with whitespace and field order ignored.

During editor operation, `OnObjectPropertyChanged` skips continuous-interaction events of type `Interactive`; other DataAsset property changes trigger export. New assets are also exported. Renaming first attempts to delete JSON at the old path, then generates it at the new path. Package reload exports the updated asset at the `PostPackageFixup` stage.

Directory monitoring attempts import only for added or modified `.json` files. The plugin first loads an existing DataAsset by path. If no asset is found, it logs a warning and returns; it does not create an asset from JSON. A JSON deletion event does not delete the asset either.

### Version-Control File Locks

.uasset files managed by Perforce or similar version-control systems may be read-only, so asset saving also needs handling.

The current implementation first calls `Modify()` within an undo transaction, writes JSON data into the in-memory asset, and calls `PostEditChange()` to notify the editor. It then checks whether `ISourceControlModule` is enabled, attempts Checkout through the current provider when enabled, and finally calls `UPackage::Save`.

The Checkout result is not checked here. Only a successful save means the asset on disk has been updated. If saving fails, the package is marked dirty and a warning is logged; changed in-memory properties alone do not establish that the file was saved.

### Deciding the Synchronization Direction

Automatic synchronization is enabled by default. After the Asset Registry finishes loading, the plugin scans DataAssets, performs initial synchronization, and then registers asset and directory monitoring for editor operation. The scan excludes assets under `/Engine/` and displays synchronization progress.

Each scanned asset is processed using its corresponding JSON path:

| File state | Synchronization action |
| --- | --- |
| JSON does not exist | Export JSON from the UE asset |
| The asset file was modified later than JSON | Export the asset and update JSON |
| JSON was modified later than the asset file | Import JSON into the existing asset and attempt to save |
| Modification times are equal | Skip |
| JSON exists but the corresponding UE asset does not | Do not create an asset from JSON. If startup scanning reaches orphan cleanup, attempt to delete the JSON. If no DataAssets are found, the current implementation returns early without cleanup |

The comparison uses the last modification times of .uasset and .json files on disk. When both sides have changed, the plugin still chooses by timestamp. It does not merge fields, and the newer file is not guaranteed to contain every change the user wants to retain.

UE determines which assets exist and their paths. Deleting a UE asset attempts to remove its JSON. Deleting only JSON does not delete the asset, and the deletion notification itself does not immediately regenerate the file. If the asset still exists, can be loaded, and automatic synchronization is enabled, the next startup exports JSON from it again. Another asset edit during editor operation may regenerate it earlier.

Startup scanning also attempts to delete orphan JSON paths absent from the scanned asset set. However, finding zero DataAssets causes an early return, skipping cleanup. Treating UE assets as the basis for existence and paths does not mean UE field values always overwrite JSON: newer JSON is still imported into existing assets under the rules above.

## Other Engineering Details

Import uses `FScopedTransaction` for undo and redo. On shutdown, the plugin unregisters `IDirectoryWatcher` and the asset and property-change callbacks, preventing listeners from retaining references to a destroyed synchronization manager.

## Practical Applications

This data channel can support AI tuning, designers' batch edits, and field-level change review. See the [AIDataAsset overview](/en/works/ai-data-asset/) for those workflows. They all require the same final step: after external edits reach the asset, test and inspect them in UE. Successful synchronization does not establish that the values or game logic are correct.
