# Letting AI Modify DataAssets Directly

## Introduction

AI is becoming deeply involved in game development. Having an LLM generate level configurations, using reinforcement learning to balance values automatically, and iterating game parameters with AI all share one prerequisite: **AI must be able to read and write game data directly**.

In UE, much game data lives in DataAssets: skill tables, character attributes, loot tables, and AI behavior parameters. However, a DataAsset is fundamentally a UE-serialized binary file (.uasset), which external tools cannot process directly. Someone must manually transfer AI-generated results into the editor. As AI iteration accelerates, this manual transfer becomes the bottleneck.

This article records my full approach to solving the problem: choosing an intermediate format, the technical pitfalls I encountered, and finally packaging it into an automated solution. Even if you do not plan to use an existing tool, these lessons can help you build a similar pipeline yourself.

## Why JSON?

Bridging DataAssets and external tools requires an intermediate format that both sides can handle. CSV, XML, and YAML are all options, but JSON is the most practical choice overall:

-   Native support in almost every programming language and AI framework
-   Human-readable and easy to debug
-   Text diffs make every field change clear during code review
-   Flexible structure that can express common nested UE data types

## UE's Built-in JSON Serialization

Many people do not realize that UE includes a fairly comprehensive JSON serialization mechanism. At its core is the `FJsonObjectConverter` utility class, with two key functions:

-   **UStructToJsonObject**: serializes any UStruct (including all UPROPERTY fields of a DataAsset) into an FJsonObject
-   **JsonObjectToUStruct**: reverses the process, deserializing an FJsonObject into a UStruct

It handles most UPROPERTY types: primitives, FString, FName, enums, nested UStructs, TArray, TMap, TSet, and even soft references (FSoftObjectPath).

**If you only need one-way, manually triggered export or import, this is enough.** An editor tool button can export JSON; after AI edits it, another click imports it. This is entirely workable.

But **automated two-way synchronization**—automatically updating JSON when a DataAsset changes in the editor, and updating the DataAsset when AI changes JSON—is much more complex.

## Pitfalls in Two-Way Synchronization

I encountered several unintuitive problems while implementing automatic two-way synchronization. Here they are, one at a time.

### Loss of Floating-Point Precision

This may be the easiest problem to overlook, and the most dangerous.

UE's default JSON serialization does not format floating-point values with enough precision. A value set to `0.3` in the editor may become `0.30000000000000004` after export. This precision drift is unacceptable for sensitive game parameters such as damage multipliers, probability weights, and physics parameters.

The solution is a custom JSON PrintPolicy. Use `%.9f` for float (9 decimal places) and `%.17g` for double (17 significant digits, the full precision of IEEE 754 double precision). This ensures values remain identical after a DataAsset → JSON → DataAsset round trip.

### Inconsistent Capitalization of Property Names

`FJsonObjectConverter` lowercases the first letter of property names during serialization: `MaxHealth` in the editor becomes `maxHealth` in the export.

This is more than cosmetic. AI sees `maxHealth` in JSON and `MaxHealth` in the editor; mismatched names make the data harder to understand. Worse, if AI writes `MaxHealth` into JSON using the editor's name, deserialization may fail to match it.

The solution is to recursively traverse all JSON fields after export and restore the uppercase initial; apply the reverse conversion before import.

### Trigger Loops

The classic two-way synchronization trap:

1.  The user changes a DataAsset in the editor
2.  A listener detects the change and automatically exports it to JSON
3.  The file system detects a JSON change
4.  A listener detects the change and automatically imports it into the DataAsset
5.  Back to step 2, forever

Breaking the loop requires two safeguards:

-   **Global synchronization flag**: set it to true while synchronization is in progress; every event handler checks it at entry and skips processing if true
-   **Tracking self-written paths**: record each file path when exporting JSON; when the file system reports a change, skip it and remove the record if its path is in the tracking list

The global flag alone is insufficient because file-system notifications are asynchronous and may arrive after it has been reset. Tracking self-writes is the key to preventing loops.

### Version-Control File Locks

On teams using Perforce or similar version-control systems, .uasset files are read-only by default. If JSON changes require a DataAsset update, writing without first checking out the asset fails.

UE provides the `ISourceControlModule` interface to perform Checkout automatically before writing, applicable to Perforce, Git, and SVN. Check that the source-control module is enabled first; not every project has source control configured.

### Deciding the Synchronization Direction

When the editor starts, both the DataAsset and JSON may have changed—for example, AI may have edited JSON while the editor was closed. You need to determine which is newer.

A reasonably reliable method compares the last modification times of the .uasset and .json files and uses the newer one as authoritative. This is correct in most scenarios because usually only one side is edited during a given period.

## Other Engineering Details

Beyond these core issues, a production-ready synchronization mechanism has many details to handle: removing JSON when an asset is deleted, comparing content before export to avoid pointless writes, wrapping JSON import in `FScopedTransaction` to support undo and redo, and managing the `IDirectoryWatcher` lifecycle to avoid dangling callbacks. Together, these represent substantial work.

## Practical Applications

**AI-driven game-data iteration**: let an LLM or reinforcement-learning system read and write JSON directly to adjust game parameters. Once AI edits JSON, the DataAsset updates automatically and can immediately be tested in the editor. One iteration shrinks from “AI generation → manual transfer → testing → feedback” to “AI generation → testing → feedback.”

**Batch tuning by designers**: designers export JSON, make batch changes in Excel or Python scripts, then put it back for automatic synchronization. This is far more efficient than opening and editing DataAssets individually, especially for global adjustments across dozens or hundreds of assets.

**Data review and version comparison**: JSON is text and naturally supports Git diff. Before submitting, you can clearly see which fields of which assets changed, making review much more intuitive than binary .uasset changes. This is especially useful for teams where designers and programmers cross-review data changes.
