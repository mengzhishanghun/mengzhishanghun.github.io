# UE: Letting AI Modify DataAssets Directly

## Introduction

AI is becoming deeply involved in game development workflows. Having an LLM generate level configurations, automatically balance values with reinforcement learning, or iterate game parameters through AI—all these scenarios share one prerequisite: **AI must be able to read and write game data directly**.

In UE, much game data exists as DataAssets: skill tables, character attributes, loot tables, and AI behavior parameters. But a DataAsset is essentially a UE-serialized binary file (.uasset), which external tools cannot process directly. AI-generated results have to be moved into the editor manually—and as AI iterates faster, this manual transfer becomes a bottleneck.

This article records my complete approach to solving this problem: choosing an intermediate format, the technical pitfalls I encountered, and finally packaging everything into an automated solution. Even if you do not plan to use an existing tool, these experiences should help you build a similar pipeline yourself.

## Why JSON?

Bridging DataAssets and external tools requires an intermediate format that both sides can handle. CSV, XML, and YAML would all work, but after weighing the options, JSON is the most practical choice:

- Native support in almost every programming language and AI framework
- Human-readable and easy to debug
- Supports text diffs, making each field change clear during code review
- Flexible structure that can express common nested data types in UE

## UE's Built-in JSON Serialization

Many people do not know that UE includes a fairly comprehensive JSON serialization mechanism. At its core is the utility class `FJsonObjectConverter`, which provides two key functions:

- **UStructToJsonObject**: Serializes any UStruct (including all UPROPERTYs in a DataAsset) into an FJsonObject
- **JsonObjectToUStruct**: Performs the reverse operation, deserializing an FJsonObject back into a UStruct

It handles most UPROPERTY types: basic types, FString, FName, enums, nested UStructs, TArray, TMap, TSet, and even soft references (FSoftObjectPath).

**If you only need one-way, manually triggered export or import, this is enough.** Write an editor tool button, click it to export JSON, and click again to import after AI modifies it. This is entirely workable in terms of functionality.

But if you need **automated bidirectional synchronization**—automatically updating JSON when a DataAsset changes in the editor, and automatically updating the DataAsset when AI changes JSON—things become much more complicated.

## Pitfalls in Bidirectional Synchronization

While implementing automatic bidirectional synchronization, I encountered several unintuitive issues. Let's examine them one by one.

### Loss of Floating-Point Precision

This may be the easiest issue to overlook, and the most dangerous.

UE's default JSON serialization uses insufficient formatting precision for floating-point numbers. `0.3` set in the editor may become `0.30000000000000004` after export to JSON. For precision-sensitive game parameters (damage multipliers, probability weights, physics parameters), this drift is unacceptable.

The solution is to customize JSON's PrintPolicy. Use `%.9f` (9 decimal places) for float, and `%.17g` (17 significant digits, the full precision of IEEE 754 double precision) for double. This ensures that values remain exactly the same after a DataAsset → JSON → DataAsset round trip.

### Inconsistent Capitalization of Property Names

During serialization, `FJsonObjectConverter` converts the first letter of property names to lowercase—`MaxHealth` in the editor becomes `maxHealth` after export.

This is more than a cosmetic issue. When AI reads `maxHealth` in JSON and then sees `MaxHealth` in the editor, mismatched field names increase the effort needed to understand them. Worse, if AI writes `MaxHealth` into JSON using the name shown in the editor, deserialization may fail to match it.

The solution is to recursively traverse every field of the JSON object after export and restore the first letter to uppercase; perform the reverse conversion before import.

### Circular Triggers

The classic trap in bidirectional synchronization:

1. The user modifies a DataAsset in the editor
2. The change is detected, triggering an automatic export to JSON
3. The file system detects the JSON change
4. The change is detected, triggering an automatic import to update the DataAsset
5. Return to step 2, looping forever

Breaking the loop requires two layers of protection:

- **Global synchronization flag**: Set it to true during synchronization. Every event handler checks it at entry and skips processing if it is true
- **Tracking self-written paths**: Record the file path when exporting JSON; when the file system reports a change, skip processing and remove the record if the path is in the tracking list

A global flag alone is insufficient—file-system change notifications are asynchronous and may arrive after the synchronization flag has been reset. Tracking self-writes is the key to eliminating loops.

### Version-Control File Locks

For teams using version-control systems such as Perforce, .uasset files are read-only by default. When JSON changes and the DataAsset needs updating, writing will fail outright without first checking out the file.

UE provides the `ISourceControlModule` interface, which can automatically perform Checkout before writing and works with Perforce, Git, and SVN. Be sure to check whether the source-control module is enabled first—not every project has source control configured.

### Determining Synchronization Direction

When the editor starts, both the DataAsset and JSON may have changed (for example, AI modified the JSON while the editor was closed). You need to determine which is newer.

A reasonably reliable method is to compare the last modification times of the .uasset and .json files and use whichever is newer as the source of truth. This is correct in most scenarios because typically only one side is modified during a given period.

## Other Engineering Details

Beyond these core issues, a production-ready synchronization mechanism has many edge cases to handle: removing the corresponding JSON when an asset is deleted, comparing contents before export to avoid unnecessary writes, wrapping JSON imports in `FScopedTransaction` to support undo/redo, managing the lifecycle of `IDirectoryWatcher` to prevent dangling callbacks… Taken together, these amount to a substantial workload.

## AIDataAsset: A Packaged Solution

If you do not want to implement this logic yourself, you can try the **AIDataAsset** plugin I developed. It packages all the issues mentioned above—floating-point precision, property-name restoration, loop protection, source-control integration, and smart writes—into a ready-to-use solution.

Usage is simple: find the AIDataAsset category in Project Settings, specify the JSON storage directory, and enable automatic synchronization. All DataAsset subclasses automatically participate, with no coding required.

Search for “**AIDataAsset**” on Fab to get it. Supports UE 5.2+, Windows / macOS / Linux.

## Practical Use Cases

**AI-driven game-data iteration**: Let an LLM or reinforcement-learning system read and write JSON directly to adjust game parameters. Once AI changes the JSON, the DataAsset updates automatically and tests can run immediately in the editor. An iteration shrinks from “AI generation → manual transfer → testing → feedback” to “AI generation → testing → feedback.”

**Batch parameter tuning by designers**: Designers export JSON, modify it in batches with Excel or Python scripts, and put it back for automatic synchronization. This is far more efficient than opening and manually editing each DataAsset in the editor, especially for global adjustments involving dozens or hundreds of assets.

**Data review and version comparison**: JSON is a text file with natural support for Git diff. Before committing, you can clearly see “which fields of which assets changed this time,” making review far more intuitive than reviewing binary .uasset changes. This is particularly useful for teams where designers and programmers cross-review data changes.
