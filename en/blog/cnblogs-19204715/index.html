UE: Say Goodbye to Loading Stutters! Merge StaticMeshActors with One Click

Introduction

When a large UE scene loads for the first time after packaging, it often suffers prolonged stutters or even appears to freeze. The reason is the enormous overhead of serializing and instantiating hundreds or thousands of separate StaticMeshActors.

This article takes a closer look at the underlying reasons ISM/HISM loads faster than separate Actors, discusses the difficulties of manual merging, and introduces an efficient workflow for breaking LevelInstances and merging StaticMeshes with one click using the SimpleStaticMeshMerger plugin.

1. The Root Cause of Loading Stutters

1.1 Loading Overhead of Separate Actors

Suppose a scene contains 500 identical trees. The traditional approach:

// 场景中：500个AStaticMeshActor
for (int i = 0; i < 500; i++)
{
    AStaticMeshActor* Tree = SpawnActor<AStaticMeshActor>();
    Tree->SetStaticMesh(TreeMesh);
    Tree->SetActorLocation(Locations[i]);
}

During loading, the engine needs to:

  1. Deserialize 500 UObjects (each AStaticMeshActor + each UStaticMeshComponent)
  2. Create 500 Components (each needs initialization and registration with the scene)
  3. Build collision bodies 500 times (each Component builds its own, even with identical collision settings)
  4. Register with the rendering system 500 times (each Component submits its rendering data separately)

Main sources of overhead:

  • UObject serialization overhead is proportional to the number of objects (500 Actors = 500 times the overhead)
  • Component initialization requires many virtual function calls and scene registrations
  • Collision bodies are built repeatedly (even with identical settings)
  • Noncontiguous memory leads to a low cache hit rate

1.2 Loading Advantages of ISM/HISM

After merging with HISM:

// 合并后：1个AStaticMeshActor + 1个UHierarchicalInstancedStaticMeshComponent
UHierarchicalInstancedStaticMeshComponent* HISM = CreateDefaultSubobject<UHierarchicalInstancedStaticMeshComponent>();
HISM->SetStaticMesh(TreeMesh);

for (int i = 0; i < 500; i++)
{
    HISM->AddInstance(FTransform(Locations[i])); // 只添加Transform数据
}

During loading, the engine needs to:

  1. Deserialize 1 UObject (1 AStaticMeshActor)
  2. Deserialize 1 HISM Component + 500 Transform matrices (as a TArray)
  3. Build collision bodies once (shared by all instances)
  4. Register with the rendering system once (submit instance data in a batch)
  5. Build an Octree (specific to HISM, for frustum culling)

Key optimizations:

  • ✅ Far fewer UObjects: 500 Actors → 1 Actor (significantly lower serialization overhead)
  • ✅ Far fewer Components: 500 Components → 1 Component (significantly lower initialization overhead)
  • ✅ Transform array serialization: contiguous memory for efficient loading
  • ✅ Shared collision bodies: built only once and reused by all instances
  • ✅ Batch rendering: render all instances in 1 DrawCall

2. The Difficulties of Creating ISM/HISM Manually

2.1 Problems with the Manual Workflow

In theory, you can manually create ISM/HISM to optimize your scene:

  1. Create an Actor and add InstancedStaticMeshComponent or HierarchicalInstancedStaticMeshComponent
  2. Add the Transforms of identical StaticMeshActors in the scene to the ISM/HISM one by one
  3. Delete the original separate Actors

But this creates serious problems:

🔴 Disrupted workflow

  • Artists can no longer place objects freely (instances must be added through code)
  • Adjusting positions requires editing the Transform array, which is extremely inefficient
  • Standard editor tools (move, rotate, duplicate) cannot be used

🔴 Error-prone property copying

  • You must manually copy Mobility, collision settings, materials, rendering settings, and more
  • Missing any setting can cause abnormal behavior after merging (such as broken collision)
  • Collision settings include responses for 32 channels, making mistakes very easy

🔴 Huge workload in complex scenes

  • Suppose a scene has 100 different Mesh types, each with dozens to hundreds of instances
  • You need to create 100 ISM/HISM Actors and manually sort thousands of objects
  • Every scene adjustment requires another manual merge

🔴 Cannot handle LevelInstances

  • Breaking nested LevelInstances in a scene manually is extremely tedious
  • After breaking one, you may discover more nested inside and have to repeat the process

2.2 The Ideal Solution

Is there a solution that can:

  • ✅ Keep the development workflow unchanged: artists still freely place StaticMeshActors using standard tools
  • ✅ Allow unrestricted scene adjustments: move, delete, or add objects at any time
  • ✅ Optimize with one final click: obtain an efficient release version through automatic merging when development is complete
  • ✅ Handle things intelligently: automatically identify Actors with matching properties and preserve their behavior after merging
  • ✅ Handle LevelInstances: automatically break nested LevelInstances

This is exactly the problem the SimpleStaticMeshMerger plugin aims to solve.

3. SimpleStaticMeshMerger: Solve All These Problems with One Click

The SimpleStaticMeshMerger plugin was created to address these difficulties, letting you keep a flexible development workflow and produce an efficiently optimized version at the end.

3.1 Core Features

1. Break LevelInstances with one click

Click the Break Level Instances button:

  • Automatically breaks all nested LevelInstances recursively
  • Displays progress in real time (Breaking: [Name])
  • Automatically refreshes the merge preview when finished

2. Intelligent grouping preview

The plugin automatically groups StaticMeshActors strictly by the following properties:

  • Mesh (same model)
  • Mobility (Static/Stationary/Movable)
  • Complete collision settings (Profile + ObjectType + responses for 32 channels)
  • Materials (materials in all slots)

3. Real-time filtering and exclusions

  • Mobility filter: show only Static/Stationary/Movable Actors
  • Minimum instance count: filter out groups with too few instances (default: 2, meaning at least 3 are required to merge)
  • Actor exclusions: uncheck Actors you do not want to merge in the list on the right

4. Merge with one click

Click the Merge Selected button:

  • Automatically creates HISM/ISM Actors
  • Copies all properties completely (collision, materials, mobility)
  • Deletes the original Actors
  • Automatically selects and navigates to the newly created Actors

3.2 Usage Demo

工作流程：
1. Window → Static Mesh Merger（打开插件窗口）
2. 点击 Break Level Instances（如果场景中有LevelInstance）

   ☑ Static  ☑ Stationary  ☐ Movable

3.3 Technical Safeguards

1. Strict property matching

The plugin checks all key properties when grouping Actors:

  • Mesh asset path
  • Mobility
  • Collision Enabled (collision enablement type)
  • Collision Profile Name
  • Collision Object Type
  • Response settings for all 32 collision channels
  • Materials in all material slots

Guarantee: Only Actors whose properties match completely are merged into the same group, avoiding abnormal behavior after merging

2. Complete property copying

During merging, all properties of the original Actors are copied completely to the newly created HISM/ISM:

  • Uses the Collision Profile first (if configured)
  • Otherwise copies collision settings individually (Enabled, ObjectType, and responses for 32 channels)
  • Copies all material slots
  • Preserves the Mobility setting
  • Copies rendering settings (shadows, outlines, etc.)

3. User experience improvements

  • Deferred refresh: avoids UI stutters caused by frequent configuration changes
  • Intelligent scene monitoring: automatically refreshes the preview when Actors change
  • Dynamic instance counts: reflects the number available for merging after exclusions in real time
  • Automatic navigation after merging: jumps to the newly created Actors for easy inspection

4. Theoretical Performance Comparison

Comparison scene: 500 identical tree models

ApproachUObject countComponent countDraw Calls
Separate Actors1000 (500 Actors + 500 Components)500500

Theoretical advantages:

  • ✅ UObject count: 500 Actors → 1 Actor (99.8% reduction)
  • ✅ Component count: 500 Components → 1 Component (99.8% reduction)
  • ✅ Draw Calls: 500 → 1 (99.8% reduction)
  • ✅ Serialization overhead: proportional to the UObject count, so it decreases significantly
  • ✅ Memory usage: each UObject has a fixed overhead, which is greatly reduced by merging

Suitable use cases:

  • ✅ Optimizing large open-world scenes
  • ✅ Batch merging vegetation and architectural decorations
  • ✅ Optimization before packaging (reducing stutters on first load)
  • ✅ Memory optimization (reducing the number of UObjects)

Notes:

  • ⚠️ Primarily optimizes loading and memory; runtime FPS improvements are limited
  • ⚠️ Merging is irreversible; version control is recommended
  • ⚠️ Only merges Actors with completely identical properties (to preserve gameplay behavior)

Summary

The loading advantages of ISM/HISM over separate Actors come from:

  1. Far fewer UObjects (lower serialization overhead)
  2. Far fewer Components (lower initialization overhead)
  3. Transforms serialized as an array (contiguous memory and fast loading)
  4. Shared collision bodies (avoiding repeated construction)

Although creating ISM/HISM manually is possible, the workload becomes enormous in complex scenes. With features such as one-click LevelInstance breaking, intelligent grouping previews, and one-click merging, the SimpleStaticMeshMerger plugin turns a tedious manual workflow into a few clicks while ensuring complete property copying and avoiding abnormal behavior after merging.

If your project suffers from loading stutters, give this plugin a try to make StaticMesh merging efficient and reliable.
