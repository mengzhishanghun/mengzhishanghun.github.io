如何让 AI 直接修改 DataAsset

探索让 AI 通过 JSON 修改复杂 DataAsset 并实时同步到 UE，讨论类型转换、双向同步、循环触发和资产写入问题。

前言

我希望把复杂的 DataAsset 数据修改交给 AI：让它读取现有配置，通过 JSON 修改基础字段、嵌套结构体和容器数据，再实时同步回 UE。这样，无论是用 LLM 生成关卡配置，还是用强化学习调整平衡数值，都能减少手工搬运数据的工作。

在 UE 中，技能表、角色属性、掉落表和 AI 行为参数常以 DataAsset 保存。DataAsset 是 UE 序列化后的二进制文件（.uasset），外部工具无法直接处理。AI 生成或修改的数值因此还要手工填回编辑器，迭代频繁时，这一步就会反复消耗时间。

为此，我用 JSON 作为中间格式，让 AI 通过文本读写数据。UE 编辑器运行时，插件监听 JSON 变化并实时写回 DataAsset，支持基础类型和大多数结构体；实现时还需要处理属性转换、变化监听和资产写入。导出、文件监听和资产回写由插件自动执行，用户无需手动导入导出；启动时的初始扫描会显示同步进度。这里记录实现双向同步时遇到的问题；工具的用途与使用场景见 AIDataAsset 作品页。

为什么是 JSON

DataAsset 与外部工具需要一种都能处理的中间格式。CSV、XML、YAML 都可以考虑，我选择 JSON，主要是因为：

  • 几乎所有编程语言和 AI 框架原生支持
  • 人类可读，方便调试
  • 支持文本 diff，需要审查数据变化时，可以比较具体字段
  • 结构灵活，能表达 UE 中常见的嵌套数据类型

JSON 默认保存在项目的 Saved/AIDataAsset/ 目录，作为后台同步的中间文件，通常不应纳入版本管理。如果希望跟踪 JSON 的字段变更，可以告诉 AI 工具修改插件配置中的 JSON Output Directory，把输出目录放到项目内需要跟踪的位置，再将 JSON 文件加入版本管理。

UE 内置的 JSON 序列化能力

UE 内置的 JSON 序列化工具类 FJsonObjectConverter 提供了两个主要函数：

  • UStructToJsonObject：将任意 UStruct（包括 DataAsset 的所有 UPROPERTY）序列化为 FJsonObject
  • JsonObjectToUStruct：反向操作，将 FJsonObject 反序列化回 UStruct

它能处理绝大多数 UPROPERTY 类型：基本类型、FString、FName、枚举、嵌套 UStruct、TArray、TMap、TSet，甚至软引用（FSoftObjectPath）。

如果你只需要单向、手动触发的导出或导入，到这里就够了。 写个编辑器工具按钮，点一下导出 JSON，AI 改完再点一下导入，功能上完全可行。

如果要让编辑器里的 DataAsset 变化自动更新 JSON，外部 JSON 变化也自动更新 DataAsset，就还需要处理双向同步。

做双向同步会踩哪些坑

实现自动双向同步时，格式转换之外还遇到了以下问题。

浮点数精度丢失

浮点数的输出格式容易被忽略，却会直接影响导出的数值。

UE 默认的 JSON 序列化对浮点数使用的格式化精度不够。编辑器里设置的 0.3，导出到 JSON 后可能变成 0.30000000000000004。对于数值敏感的游戏参数（伤害系数、概率权重、物理参数），这种精度漂移不可接受。

解法是自定义 JSON 的 PrintPolicy。对 float 使用 %.9f（9 位小数），对 double 使用 %.17g（17 位有效数字，IEEE 754 双精度的完整精度）。这样可以保证 DataAsset → JSON → DataAsset 的往返转换后数值完全一致。

属性名首字母大小写不一致

FJsonObjectConverter 在序列化时会将属性名的首字母转为小写——编辑器里的 MaxHealth 导出后变成 maxHealth。

这不只是美观问题。AI 读到 JSON 中的 maxHealth，再看编辑器里的 MaxHealth，字段名对不上会增加理解成本。更麻烦的是，如果 AI 按编辑器里看到的名字写了 MaxHealth 到 JSON，反序列化时可能匹配不上。

解决方案是在导出后递归遍历 JSON 对象的所有字段，将首字母还原为大写；导入前做反向转换。

循环触发

双向同步可能沿着这条路径反复触发：

  1. 用户在编辑器里改了 DataAsset
  2. 监听到变化，自动导出写入 JSON
  3. 文件系统检测到 JSON 变化
  4. 监听到变化，自动导入更新 DataAsset
  5. 回到步骤 2，无限循环

实现中用了两层防护：

  • 同步标记 bIsSyncing：启动同步和处理目录变更时设为 true。资产属性、新增、删除、重命名及包重载回调发现正在同步就返回，避免导入过程中再次导出。
  • 自写入路径集合 PendingSelfChanges：导出实际写入文件后记录规范化路径。目录监听收到该路径的通知时，移除标记并跳过这条通知，避免把自己的导出当作外部修改。

文件系统通知可能晚于同步标记复位，所以还需要路径追踪。导出前会比较已有文件与新生成的 JSON 文本，导入前也会比较当前资产的序列化文本与文件内容；字符串完全一致就跳过。这里比较的是文本，不是忽略空白和字段顺序后的 JSON 语义。

运行期间，OnObjectPropertyChanged 跳过 Interactive 类型的连续交互事件，其余 DataAsset 属性变更会导出；新增资产也会导出。重命名先尝试删除旧路径 JSON，再生成新路径 JSON；资产包重载则在 PostPackageFixup 阶段导出更新后的资产。

目录监听只对 .json 的新增和修改事件尝试导入。插件先按路径加载已有 DataAsset，找不到资产就记录警告并返回，不会根据 JSON 新建资产；JSON 删除事件也不会触发资产删除。

版本控制文件锁定

Perforce 等版本控制系统管理的 .uasset 文件可能处于只读状态，因此还要处理资产保存。

当前实现先在撤销事务中调用 Modify()，将 JSON 数据写入内存资产，再调用 PostEditChange() 通知编辑器。随后检查 ISourceControlModule 是否启用，启用时通过当前 provider 尝试 Checkout，最后调用 UPackage::Save 保存。

这里没有检查 Checkout 的返回结果。保存成功才表示磁盘资产已更新；保存失败会将包标记为待保存并输出警告，不能仅凭内存中的属性变化认定文件已保存。

同步方向判断

自动同步默认开启。插件等待资产注册表加载完成后，先扫描 DataAsset，再执行初始同步，最后注册运行期间的资产和目录监听。扫描会排除 /Engine/ 下的资产，并显示同步进度。

对每个扫描到的资产，按对应 JSON 路径处理：

文件状态同步动作
JSON 不存在从 UE 资产导出 JSON
资产文件修改时间晚于 JSON导出资产，更新 JSON
JSON 修改时间晚于资产文件导入 JSON，修改已有资产并尝试保存
修改时间相同跳过
JSON 存在，对应 UE 资产不存在不会根据 JSON 创建资产；启动扫描进入孤立文件清理阶段后，会尝试删除该 JSON。若没有扫描到任何 DataAsset，当前实现会提前返回，不执行清理

比较的是磁盘上 .uasset 和 .json 文件的最后修改时间。两端都改过时，插件仍按时间戳选择方向，不会合并字段，也不保证时间较新的文件一定包含用户想保留的全部修改。

资产的存在关系和路径以 UE 为基础：删除 UE 资产时，插件会尝试清理对应 JSON；只删除 JSON 不会删除资产，删除通知本身也不会立即重建文件。资产仍存在、可加载且自动同步开启时，下次启动会从资产补回 JSON，运行期间再次修改资产也可能提前补回。

启动扫描还会尝试删除不在本轮资产路径集合中的孤立 JSON。不过，当前实现发现 DataAsset 数量为零时会提前返回，不执行这一步清理。以 UE 资产为主并不意味着始终以 UE 字段值覆盖 JSON：较新的 JSON 仍会按上表导入已有资产。

其他工程细节

导入通过 FScopedTransaction 支持撤销和重做；插件关闭时注销 IDirectoryWatcher 以及资产、属性变化等回调，避免监听器继续引用已销毁的同步管理器。

实际应用场景

这条数据通道可以用于 AI 调参、策划批量修改和字段差异审查，具体流程见 AIDataAsset 作品页。对实现来说，这些用途都依赖同一件事：外部修改写回资产后，仍要在 UE 中测试和检查，不能把同步成功当作数值或游戏逻辑已经正确。
